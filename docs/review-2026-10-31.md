# Архитектурный обзор — 31 октября 2026

Первый обзор по постоянной задаче дорожной карты. Состояние: версия 0.25.0, все задачи этапов 0–6 закрыты, 19 миграций, 61 маршрут API, 17 экранов, 488 тестов Vitest (плюс 16 проверок этого обзора) и 11 сценариев Playwright. Обзор фиксирует, как устроен код на самом деле, где он разошёлся с концептом и какой долг стоит гасить в ближайших запусках. Правила, которые решено держать, закреплены тестом `tests/architecture.test.ts` — он падает не когда «сломалось», а когда границы сдвинулись.

## 1. Как устроен код

Репозиторий — один, слоёв четыре, и они не пересекаются.

| Слой | Где | Объём | Что внутри |
|---|---|---|---|
| Предметная логика и хранилище | `functions/_lib/*.ts` (23 модуля) | 7 260 строк | Каждый модуль — одна область: типы, интерфейс `XStore`, его реализация `d1XStore(db)` на D1, чистые функции и подсказки модели |
| Маршруты | `functions/_lib/app.ts`, точка входа `functions/api/[[route]].ts` | 808 строк | `createApp(version, makeStore)` — Hono, 61 маршрут, склейка пятнадцати хранилищ в один `Store` |
| Worker рассылки | `workers/digest/index.ts` | 81 строка | cron `*/15`, переиспользует `digest.ts` и `push.ts` из `_lib`, в D1 — только `select 1` для проверки связи |
| Фронт | `src/*.ts` (навигация, клавиши, голос, тема, офлайн, установка), `src/screens/*.tsx` | 2 085 + 3 039 строк | Один клиент `src/api.ts` (411 строк, все типы ответов), экраны — функции над ним, `App.tsx` держит одно состояние экрана через историю браузера (`nav.ts`) |

Граф импортов: `functions/_lib` — 23 модуля, 7 из них без зависимостей (`auth`, `providers`, `onboarding`, `fsrs`, `mail`, `extract`, `release`), ядро — `items` (его тянут 11 модулей), `assessment` и `cards` (по 10), `scoring`, `program`, `profile`. `app.ts` импортирует 20 модулей и больше никто его не импортирует, кроме точки входа и тестов. Фронт и API друг друга не импортируют — только HTTP. Внешних пакетов в API два: `hono` (только в `app.ts`) и `unpdf` (динамический импорт в `extract.ts`).

Циклов во время выполнения нет. Есть три цикла только через типы: `scoring ↔ cards` (`WritingError` в одну сторону, `CARD_TOPICS` в другую), `scoring ↔ assessment` (`Attempt`), `Checkpoint.tsx ↔ Assessment.tsx` (`Mode`). Они безвредны, но показывают, что общие типы оценивания живут не в своём модуле.

Тесты: 35 файлов до обзора, каждый модуль `functions/_lib` и каждый модуль `src/*.ts` задействован хотя бы в одном тесте. Хранилища проверяются двумя способами — `memoryStore` (248 строк, повторяет семантику SQL в памяти) для быстрых API-тестов и `sqliteD1` (node:sqlite с полным набором миграций) в одиннадцати файлах тестов для настоящего SQL. Экраны проверяются Playwright-сценариями в Actions перед деплоем; React-компоненты вне экранов (`App`, `KeyHints`, `Recorder`, `ThemeSwitch`) отдельных тестов не имеют и покрыты только сценариями.

## 2. Что сделано хорошо и менять не нужно

Границы слоёв чистые: предметная логика не знает о Hono, экраны не знают о D1, Worker собран из тех же модулей, что и API. Это позволило за один запуск поставить Playwright-стенд из `dist` и `createApp(memoryStore)` без wrangler — архитектура выдержала.

Интерфейсы хранилищ (`AuthStore`, `LessonStore` …) с двумя реализациями — D1 и память — дали дешёвые тесты и честный тестовый стенд. Проверка настоящего SQL через `node:sqlite` закрывает главный риск этого подхода — расхождение памяти и базы.

Доменные ошибки — классы `XError` с кодом и HTTP-статусом внутри модуля, маршруты только переводят их в ответ. Коды ошибок стабильные и описаны в CHANGELOG.

Версия одна во всех местах (package.json, точка входа API, Worker, Tauri, Cargo) и поднимается по semver; миграции только добавляются. Оба правила теперь под тестом.

## 3. Расхождения с концептом

Концепт (`docs/concept.md`, раздел 5) писался до реализации; часть решений изменилась, и это стоит зафиксировать, чтобы следующий обзор не считал их ошибками.

Фронт без Tailwind, shadcn/ui, Framer Motion и Recharts: один `styles.css` на 331 строку с переменными дизайн-проекта, радар и лестница — рукописный SVG. Зависимости меньше, бандл меньше, дизайн-проект соблюдается напрямую через переменные цвета. Менять не стоит.

R2 для резюме и аудио не используется: резюме не хранится вовсе (только извлечённый текст в `profiles.resume_text`), запись голоса уходит в Whisper и не сохраняется. Это лучше для приватности и проще; R2 понадобится, только если захотим слушать свои ответы задним числом.

KV для сессий и ключей не используется: сессии — таблица `sessions` в D1 (хэши токенов), ключи провайдеров — таблица в D1, зашифрованные мастер-ключом. Одно хранилище вместо двух, транзакции с остальными данными. Менять не стоит.

Голосовая репетиция (4.1 «текст + голос») реализована как голосовой ответ на любой вопрос, а не отдельный голосовой режим; беглость речи оценивается по записям. Это ближе к пожеланию Юрия от 30.10, чем к первоначальному концепту.

Предложение: при следующей правке `docs/concept.md` обновить таблицу раздела 5 (фронт — свой CSS и SVG; данные — только D1; голос — на любом вопросе). Сделано в 0.25.7.

## 4. Долг

По убыванию отдачи от исправления.

**`app.ts` растёт линейно с числом маршрутов.** 808 строк, 61 маршрут, 50 блоков `try/catch`, семь почти одинаковых функций `xFail(c, e)` — по одной на область. Пока это читаемо, но каждая новая область добавляет ещё одну. Решение: один `app.onError`, который узнаёт любой `XError` по полям `code` и `status` (сделать общий базовый класс `DomainError` в `_lib/errors.ts`), и вынос маршрутов по областям в `functions/_lib/routes/*.ts` с `app.route('/lesson', lessonRoutes)`. Бюджет теста: 900 строк и 70 маршрутов — при следующих двух-трёх задачах с новыми маршрутами разбиение станет обязательным.

**Общие типы оценивания размазаны.** `Attempt`, `WritingError`, `CARD_TOPICS`, `Mode` дают три цикла через типы. Решение: `_lib/types.ts` (или расширить `items.ts`) для `Attempt` и `WritingError`; `Mode` теста/среза — в `src/api.ts` рядом с типами ответов. Небольшая правка, снимает все три цикла; тест фиксирует список участников циклов и не даст появиться новым.

**`memoryStore` — второе хранилище на 248 строк.** Каждое новое поле профиля или таблица правятся в трёх местах: миграция, `d1XStore`, `memoryStore`. Расхождение ловит только `sqliteD1`. Решение не рефакторить, а сузить: API-тесты и Playwright-стенд постепенно переводить на `sqliteD1` (в Node 22 он есть, в Actions — тоже), `memoryStore` оставить для юнит-тестов чистых функций. Это снимет необходимость поддерживать два хранилища.

**Три крупных модуля по 600–660 строк** — `assessment.ts`, `rehearsal.ts`, `lesson.ts` — совмещают типы, хранилище, подсказки модели и логику шага. Бюджет 900 строк в тесте даёт запас; при следующем росте первым делом выносить тексты подсказок (`PROMPTS`) в соседний файл — они самые длинные и меняются чаще логики. Для `rehearsal.ts` сделано в 0.25.18 (`rehearsal-prompts.ts`); у `assessment.ts` и `lesson.ts` своих подсказок нет.

**Секция e2e не покрывает половину экранов.** В сценариях: вход, главный, занятие, тест, настройки, телефон, /install. Нет репетиции, среза, программы, банка, журнала, достижений, письма и push, резюме и анкеты. Эти экраны проверяются только Vitest-тестами модулей и руками Юрия. Решение: по одному сценарию на запуск в рамках постоянной задачи, начиная с репетиции и среза (больше всего логики на экране).

**Версия живёт в пяти файлах.** Тест теперь ловит расхождение, но править всё равно пять мест. Решение не срочное: фронт версию уже не хранит — показывает её из `/api/health`; для Functions и Worker можно читать `package.json` на сборке (`define` в конфигурации сборки или шаг workflow, который подставляет `VERSION` перед `wrangler pages deploy`). Tauri и Cargo останутся отдельными — их читает другой инструмент.

**Тесты не проверяются `tsc`.** `tests/` не входят ни в один tsconfig, Vitest транспилирует их esbuild без проверки типов — ошибка типа в тесте проявится только как падение во время выполнения или не проявится вовсе. Решение: `tsconfig.tests.json` с `include: ["tests"]` и скрипт `lint:tests`, вызывать в шаге тестов workflow.

**Логи Actions из облачной сессии не читаются**, поэтому workflow оброс аннотациями (`deploy.yml` — 272 строки, Deep check — восемь `notice`). Это не долг кода, а условие среды; но стоит вынести дымовые проверки из YAML в скрипт `scripts/smoke.mjs`, который печатает аннотации сам — YAML станет короче, а проверки можно будет гонять локально против стенда.

## 5. Что закреплено тестом

`tests/architecture.test.ts` проверяет: фронт и API не импортируют друг друга; Worker импортирует только `functions/_lib`; `hono` знает только `app.ts`, точка входа Pages импортирует только `app.ts`; SQL (`.prepare(`) пишут только модули `_lib`; внешние пакеты API — только `hono` и `unpdf`; циклов во время выполнения нет, а циклы через типы — только известные пять файлов; семь базовых модулей без зависимостей; бюджеты размера (модуль `_lib` ≤ 900 строк, экран ≤ 500, `api.ts` ≤ 500, `app.ts` ≤ 900 строк и ≤ 70 маршрутов); каждый модуль `_lib` и `src/*.ts` задействован в тестах; версия одна в пяти файлах и есть раздел в CHANGELOG; миграции нумеруются сплошь, старые не меняются (снимок сумм `tests/migrations.sha256`), новые не содержат `DROP`, `DELETE`, `UPDATE`, `ALTER … DROP/RENAME` без явного исключения; служебный засев стенда (`/__e2e`) не попадает в `app.ts`.

Чтобы осознанно поменять правило — правится тест и этот раздел обзора в одном коммите.

## 6. Предложения в дорожную карту

В раздел «Постоянно» добавить подпункты, по одному на запуск: `app.onError` с общим `DomainError` и вынос маршрутов по областям; общие типы оценивания в один модуль (снять три цикла); `tsconfig.tests.json` и проверка типов тестов в Actions; сценарии Playwright для репетиции и среза, затем программы и банка; дымовые проверки из YAML в `scripts/smoke.mjs`; обновить раздел 5 концепта по фактическим решениям.
